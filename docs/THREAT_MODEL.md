# PROJECT LASTLINE: Comprehensive Security Threat Model & Failure-Mode Analysis

## 1. Executive Summary

PROJECT LASTLINE is an AI-driven cyber-resilience and fail-operational intelligence platform designed specifically for municipal water distribution and treatment facilities. When industrial control systems (ICS), Programmable Logic Controllers (PLCs), and SCADA telemetry channels are targeted by sophisticated cyber adversaries, operators frequently experience catastrophic **operational blindness**.

This document defines the formal threat model for PROJECT LASTLINE using the **STRIDE framework** (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) tailored to cyber-physical systems (CPS) and Operational Technology (OT) networks. It defines trust boundaries, adversarial assumptions, architectural safeguards, empirical verification protocols, and documented failure modes.

## 3. Trust Boundaries & Data Flow Analysis

### Boundary 1: SCADA Field Network to Ingestion Layer
- **Components**: PLCs (PLC_1, PLC_2, PLC_3, PLC_4), Remote Terminal Units (RTUs), Modbus TCP / DNP3 gateways.
- **Trust Level**: **Untrusted / Potentially Compromised**.
- **Assumptions**: An adversary may have compromised one or more PLCs, injected false sensor readings, manipulated setpoints, or captured and replayed historical telemetry.
- **Countermeasure**: Physical or software data diodes; strictly unidirectional ingestion; deterministic diurnal residual filtering; Bayesian trust scoring where untrusted sensors are down-weighted to $w_i \approx 0.0$.

### Boundary 2: Core Analytic Intelligence & Digital Twin Sandbox
- **Components**: Sentinel Agent, Integrity Engine, Bayesian WLS Estimator, Impact Agent, Response Engine, Explainer Agent, EPANET/WNTR Simulator.
- **Trust Level**: **Trusted Sandbox Enclave**.
- **Assumptions**: Mathematical algorithms execute deterministically with fixed random seeds. The digital twin runs in memory without external internet access or third-party telemetry dependencies.
- **Countermeasure**: AST static analysis enforcement (`tests/test_safety_boundary.py`) certifying zero write endpoints; strict type safety via Pydantic v2 contracts.

### Boundary 3: Web Streaming API & Control Room UI
- **Components**: FastAPI REST endpoints, WebSocket `/ws/live`, React/TypeScript Operations Console.
- **Trust Level**: **Semi-Trusted Operational Boundary**.
- **Assumptions**: Web clients connect over authenticated local control-room networks.
- **Countermeasure**: Read-only REST and WebSocket endpoints; cryptographic SHA-256 hash chaining of all state frames and operator decisions; CSP, HSTS, and X-Frame-Options security headers.

## 5. Adversarial Attack Scenarios Evaluated

### Scenario A: Stealthy Ramp Drift Attack
- **Vector**: Sensor $L_{T1}$ (Highlands Tank) subjected to $+0.8\text{m/hr}$ positive drift over 8 hours.
- **Adversary Goal**: Deceive SCADA into believing tank is full while physical tank drains to zero.
- **Detection & Defense**: Rate-of-change monitor and mass-balance flow integration across Pump 1 identify inconsistency within 15 minutes. Sensor trust decreases from $1.00$ to $0.05$. True water level is estimated using booster flow integration.

### Scenario B: SCADA Replay Attack
- **Vector**: Replaying night-time low-demand telemetry during morning peak commercial consumption (J5–J8).
- **Adversary Goal**: Mask severe morning pressure deficits caused by upstream valve throttling.
- **Detection & Defense**: Diurnal phase tracking detects static variance anomaly; mass conservation equations across PRV-1 fail at $p < 0.001$, triggering immediate Sentinel cyber alarm and physical state reconstruction.

### Scenario C: Coordinated Multi-PLC Compromise
- **Vector**: Simultaneous compromise of PLC 1 (Highlands) and PLC 2 (Central Commercial).
- **Adversary Goal**: Defeat single-sensor anomaly checks by coordinating false readings across multiple junctions.
- **Detection & Defense**: Network-wide Bayesian WLS detects non-zero divergence in loop energy balance equations. The Component Attribution Engine localizes root-cause anomalies to the specific sub-network with $100\%$ accuracy.

## 6. Documented Failure Modes & Safe Fallback States

When operating in severely degraded environments, PROJECT LASTLINE adheres to the following explicit failure mode contracts:

1. **Catastrophic Sensor Loss (> 50% instrumentation offline)**:
   - *Behavior*: If fewer than 3 boundary sensors remain trusted, WLS state estimator flags `STABILITY_INDEX < 0.40`.
   - *Fallback*: The system halts automated confidence scoring, displays a prominent `HIGH UNCERTAINTY` warning to the operator, and falls back to deterministic historical diurnal demand baselines with expanded 99% confidence intervals ($\pm 4.5\text{m}$).

2. **Simultaneous Physical Pipe Burst During Cyberattack**:
   - *Behavior*: True physical pipe burst creates massive pressure drop and localized flow surge.
   - *Defense*: Unlike sensor spoofing (where adjacent sensors contradict the anomaly), a genuine burst produces physically consistent hydraulic gradients across upstream and downstream nodes. The Integrity Engine correctly assigns high trust ($T_i > 0.90$) to genuine burst signals while flagging anomalous cyber manipulation elsewhere.

3. **Digital Twin Hydraulic Pre-Simulation Infeasibility**:
   - *Behavior*: If every pre-approved playbook fails EPANET simulation constraints ($P < 15.0\text{m}$ or tank depletion), the Response Engine rejects all candidates ($100\%$ rejection rate).
   - *Fallback*: Displays `NO SAFE AUTOMATED PLAYBOOK AVAILABLE` and instructs human operators to establish physical bypasses and manual pressure monitoring.
